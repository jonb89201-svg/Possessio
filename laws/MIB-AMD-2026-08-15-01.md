## What the taxonomy already holds, and what it misses

Amendment VIII gave us the **False Green**: a check that reports protection it does not perform.
The 851 vacuous tests. The placeholder TWAP returning a constant. `MockCbETH.withdraw()` against
an asset with no on-chain redemption.

PHYSICS_of_law's standing test added **disclosed ungated area** — a place the law deliberately
does not reach, said out loud. And the migration near-miss added the **unmapped surface** — no
lie, no gate, and nothing shaped to notice one was missing.

**None of the three covers a check that passes correctly and then stops.**

The market cap tracked truthfully for nine minutes. Every tick inside that window was accurate.
No test lied. No gate was missing. And the number on the console was frozen for a month, because
the pass had a **bound nobody had named** — the time-stop measured age from birth rather than
from qualification, so tracking was already most of the way through its budget the moment it
began.

That is a distinct class, and it is the most expensive one in this protocol's record: **a green
whose timer had not run out at the moment of observation.**

## Core Principle 7 — Ratification by Bounds

**A pass is not ratified until its bound is stated.**

Every green has a condition under which it stops. If that condition cannot be named, the green
has not been measured — it has been *caught early*. Observing correct behaviour proves the
behaviour occurred; it does not prove the behaviour persists, and the two are routinely confused
because they produce identical evidence at the moment of observation.

The question is therefore not only "does it work" but **"what makes this stop, and have I seen
that limit?"**

### The operational form

A ratified claim carries its kill condition alongside its result.

| unratified | ratified |
|---|---|
| `posted=45` | `posted climbing · bound: token match holds` |
| "the socket is up" | "socket up · bound: linked wallet ≥ 0.02 SOL, degrades silently below" |
| "the keeper is live" | "keeper live · bound: gas balance, currently 0.038 SOL" |
| "tracking works" | "tracking works · bound: time-stop window, anchored to qualified_ms" |
| "the tape costs nothing" | "tape free · bound: ACTIVE_MINTS empty; any mint set resumes metering" |

### Why it is enforceable rather than advisory

Because in every instance in this protocol's record, **the bound existed and was discoverable
before the failure.** Not one was unknowable at ship time:

- the mc ceiling was a variable choice at `screen.ts:673`
- the PumpPortal stream's bound was published in the vendor's own docs
- the keeper's bound is its balance, readable on chain
- the tape's bound is a variable in its own banner

The bound was always in reach. It was never asked for. That is what makes this a discipline and
not an aspiration — the question has an answer every time, and asking it costs one line.

### What it does NOT require

It does not require proving the bound will never be reached. It requires **naming it**. A bound
that is known and accepted is a ratified pass; a bound that is unknown is not a pass at all.

Nor does it require a new test framework. It requires that a reported result state its own
expiry, the same way §I.2 requires that an untested feature be reduced or removed.

## Relation to the existing principles

**Position 1 (honesty as root)** — an unbounded green is not dishonest, but it is *incomplete in
a way that reads as complete*. Same surface, missing half.

**Position 2 (if it can't be tested it doesn't exist)** — this is that principle on the time
axis. A thing can exist for nine minutes and pass its test. Existence was never the whole
question; **duration** is the other half.

**Position 6 (no softening)** — the correction is expensive here. Stating a bound often reveals
that a thing thought finished is not, and that is precisely when the discipline is load-bearing.

---

## Cost of its absence, stated by the Architect

Three weeks. In this protocol that is the distance from concept to deployment to V2 — the same
span that produced PLATE V1 from an unaudited file to live mainnet.

# PART TWO — §III addendum: the Cloudflare Worker sequence

**Affects:** §III Terminal Command Discipline — adds a named sequence alongside the
fresh-terminal Foundry sequence.
**Ratified:** August 15, 2026 — same instrument as Part One.

## Why this is in the laws and not in someone's memory

§III already carries the fresh-terminal Foundry sequence verbatim, and nobody re-derives it.
There was no equivalent for Cloudflare Workers, so it was rebuilt from scratch every time — by
seats that do not have the memory, from sessions they have to search for. On 2026-08-14 that
cost the Architect four searches across four sessions to reassemble a sequence every step of
which was already known.

**Two commands became thirteen. Every one of them had been run before.** That is the whole
argument for writing it down.

## The sequence — MEASURED 2026-08-14, this exact run

Fresh terminal, repo root.

**1. Node check.** Wrangler needs v22+; v24 is fine.
```
node --version
```
Only if below v22: `sudo apt-get update && sudo apt-get install -y npm`, then
`nvm install 22`, then `nvm use 22`.

**2. `mib-reports/` does not exist in a fresh container.** It is not in the repo. Create it
before any `tee`, or the redirect fails with *No such file or directory*.
```
mkdir -p mib-reports
```

**3. Into the Worker directory.** Not the repo root — `wrangler` reads the config from here.
```
cd radar
```

**4. Dependencies**, if the container is fresh.
```
npm install
```

**5. Verify auth BEFORE spending a long command on it.**
```
npx wrangler whoami
```
Expect account name and email. **Measured 2026-08-14: auth resolved on its own with no export.**
If it fails, `export CLOUDFLARE_API_TOKEN="<paste>"`, then `echo ${#CLOUDFLARE_API_TOKEN}` as the
truncation check, then re-run `whoami`.

Why this step earns its place: on 2026-08-05, `whoami` **succeeded** while `secrets-store store
create` failed with API error 10000. The *difference* between those two results is what
diagnosed a missing permission rather than a bad token. A green `whoami` next to a red command
is a scope finding, not an auth failure.

**6. Set the secret.** Prompts, does not echo.
```
npx wrangler secret put <NAME>
```

**7. Deploy.**
```
npx wrangler deploy 2>&1 | tee ../<name>_deploy.txt
```
Expect `Deployed`, a workers.dev URL, and a Current Version ID.

**OPEN — do not canonize either answer yet.** Whether a secret-only change requires step 7 is
**unresolved**. Fathom states it takes effect immediately with no redeploy; every working
sequence in the record includes the deploy. On 2026-08-14 both were run, so the question was not
isolated and remains unanswered. Per the May 2026 ratification refusal on `sed -i`: **a single
observation is insufficient.** Written here as a question, not an instruction.

## Rules that survived the run

**Secrets never route through a seat.** When a secret must exist, a seat supplies the *command
to make one*, never the value. `openssl rand -hex 32` is the deliverable. This held for the
keeper key and was breached once for `TAPE_INGEST_TOKEN` — a value arrived pasted rather than
generated, and was burned by the roll-on-leak rule as a result.

**Prefer one source over two pastes.** When the same secret must exist in two places, copy it
from the side that already holds it rather than generating a third copy. On 2026-08-14 a
generated value was pasted into both Cloudflare and Railway and they did not match — a 401 that
survived hours. It cleared the moment the value was copied out of Railway's reveal and pasted
into `wrangler secret put`. **One source cannot mismatch itself.**

**Terminal text does not select on mobile.** This is the constraint that shapes everything above.
Anything that must be copied has to reach an editor tab or a downloadable file first — terminal
output cannot be copied on the Architect's substrate. A sequence that ends in "copy this from
your terminal" is not executable here, regardless of correctness.

**Merging is not deploying, and it differs per service.** MEASURED 2026-08-14: Railway services
tracking `main` auto-deploy on merge. The `possessio-radar` Worker deploys on a 3-hour cron and
`workflow_dispatch` only — a merge does **not** deploy it. Any change to that Worker requires a
manual Actions trigger, or it sits idle for up to three hours while looking merged.

This is Ratification by Bounds applied to deployment itself: *merged* is a state with a bound,
and the bound is per-service.
