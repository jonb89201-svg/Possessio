## Background

Before this amendment, MIB Section III documented terminal command discipline focused on **producing** correct output: one command at a time (Rule 1), exact step sequences (Rule 2), uninterrupted output (Rule 3), explicit push verification (Rule 4), and avoiding stall commands (Rule 5). File verification discipline addressed the produced artifacts (raw URLs over browser cache, uploaded report.txt as authoritative).

What was undocumented: **how to query a produced report artifact on a mobile device when the report is hundreds or thousands of lines long.**

The canonical V2 baseline at 621 tests across 23 suites produces a `report.txt` exceeding 60 KB. The full report is unreadable on a phone screen via standard `cat` or `less` — it scrolls past the terminal buffer faster than the device can render, and finding specific test results requires scrolling through unrelated suite output.

Without surgical query methodology, every test report review on mobile is either:
- A full top-to-bottom scroll (bandwidth-intensive, error-prone)
- An upload-to-AI-seat operation (cycle time + interpretation drift)
- Trust in the summary line alone (loses substrate visibility on which specific tests passed/failed)

The `tee` + `grep` methodology removes that friction.

## Rule 6: Surgical Test Report Query

**`tee` writes test output to file as it streams; `grep` extracts surgical substrate from the file after.**

The canonical MIB 14-step sequence (MIB-AMD-2026-05-16-01, Step 14) already produces the artifact:

```
forge test -vv | tee report.txt
```

This pipes the streaming `forge test` output to both the terminal (live visibility) AND to `report.txt` (persistent artifact). Once `report.txt` exists on disk, surgical queries operate on the artifact, not on the live stream.

### Canonical query patterns

**Summary verification — final pass/fail count:**
```
grep -E "tests passed|tests failed|Suite result" report.txt | tail -30
```

**Suite-by-suite breakdown:**
```
grep -E "^Ran [0-9]+ tests for|Suite result" report.txt
```

**Find a specific test by name:**
```
grep -B 2 -A 2 "test_SameBlockReplayBlocked" report.txt
```

**Find all failing tests across all suites:**
```
grep -E "\[FAIL\]" report.txt
```

**Locate the suite a specific test belongs to:**
```
grep -B 50 "test_SpecificTestName" report.txt | grep "Ran [0-9]+ tests for" | tail -1
```

**Pull all tests passing in a single suite:**
```
grep -A 200 "Ran [0-9]+ tests for test/AutomationInvariants.t.sol" report.txt | grep "\[PASS\]"
```

**Selector-level audit when a revert fires:**
```
cast 4byte 0xc2e2c002
```
Cross-reference output against contract's custom error definitions to identify which protection fired.

**Count substrate to verify totals match:**
```
grep -c "\[PASS\]" report.txt    # should match passed count in summary
grep -c "\[FAIL\]" report.txt    # should match failed count in summary
```

### Composability discipline

`grep` flags compose:
- `-E` for extended regex (alternation with `|`)
- `-B N` for N lines BEFORE the match
- `-A N` for N lines AFTER the match
- `-c` for count only
- `-n` for line numbers
- `-i` for case-insensitive

Combine surgically. Avoid `grep` chains that produce more output than the original report — defeats the purpose.

### What this enables

- **Mobile readability.** A surgical query returns 1-30 lines, fitting on a phone screen.
- **Audit trail.** The `report.txt` file persists; queries can be re-run, results compared across builds.
- **Substrate honesty.** "621/0/0" summary is verified against `grep -c "\[PASS\]"` count match — no trust in summary alone.
- **Differential debugging.** When a fix is ratified, `grep "test_TargetTest" old_report.txt new_report.txt` shows the before/after state directly.
- **Architect-and-council coordination.** Architect can pull the surgical substrate needed for a routing decision without uploading the entire report.

### Discipline boundaries

**Do not chain `grep | grep | grep` deeply.** If a query needs three or more pipes, restructure as a single composed regex or a two-step query.

**Do not use `grep` to validate substrate that requires structural reading.** Surgical extraction is for known-pattern lookup. If you need to understand WHY a test failed (not just THAT it failed), read the surrounding context (`-B 20 -A 20`) or open the file with a tool that handles structure.

**Do not skip terminal-output verification by querying a stale `report.txt`.** Each test run produces its own report. Re-running tests requires re-running `tee`. Per Codebyte Amendment VII, terminal output of the CURRENT run is authoritative; an old `report.txt` is historical reference, not verification.

### Why `tee` and not just `>`

`tee` writes to file AND prints to stdout. Standard redirect (`>`) writes to file only — silent execution on mobile means no visibility into long-running tests. The `tee` discipline maintains live visibility AND produces the queryable artifact. **The pattern is non-negotiable in MIB context: always `| tee report.txt`, never just `> report.txt`.**

The `tee` + `grep` test report query methodology emerged organically during the May 20, 2026 session processing the report_46 canonical baseline (621 tests / 23 suites / 0 failed / 0 skipped). The Architect named it as load-bearing for MIB after observing it in active use; this amendment ratifies the methodology as canonical operational discipline.

Substrate-honest note: this methodology builds on prior MIB substrate:

Earlier instances established the `| tee report.txt` discipline as a canonical step. This amendment documents the **next operation** in the chain — what to do with `report.txt` once it exists. The combination of those substrates is what makes mobile surgical audit possible.

Whether earlier instances used `grep` queries on `report.txt` as canonical practice is unknown to this session; the Architect adjudicates whether this amendment formalizes a continuation or a discovery. Either way, the methodology is now canonical MIB substrate.

## Implications

**Mobile audit cycle time** drops from minutes (full report scroll or upload-then-interpret) to seconds (one or two `grep` queries). Across many test runs in a build arc, this compounds into substantial bandwidth preservation.

**Architect-side substrate access** improves. The Architect can pull surgical substrate from any report.txt without needing a council seat to interpret it. This is load-bearing for the discipline boundary on Architect-doesn't-write-code — the Architect needs direct read access to terminal substrate to adjudicate without compromising the boundary.

**Council-seat substrate access** improves. AI seats receiving an uploaded report.txt can ground their analysis in surgical substrate rather than full-document interpretation. The substrate-honesty discipline holds tighter when queries are surgical (each claim grounded in a specific `grep` result) rather than impressionistic (claims grounded in "what the report seems to say").

**Test report becomes living substrate.** Same report.txt, queried different ways at different times, produces different surgical extractions. The artifact gains more utility over its lifetime than the original `forge test` produced at runtime.

## Discipline reminder

This amendment is operational discipline, not contract code. It changes how the Architect and council members operate; it does not change what the contracts do. Per Codebyte Law, contract behavior is the canonical substrate; spec, report, and query methodology are all downstream. If a `grep` query disagrees with the actual contract behavior, the contract wins.

The methodology is also a tool, not a substitute for reading source. Surgical queries extract substrate; understanding the substrate requires reading the source the substrate refers to.
