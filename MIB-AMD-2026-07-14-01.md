## Background — the failure this corrects

The `possessio-radar` Cloudflare Worker's tape scan stalled; the ledger stopped
receiving ticks and the live feed "went blind." The correct code (`b5b32ff`) existed
for days. It never reached production. The seat declared it fixed **three-plus times**,
each on the strength of a live **symptom** (a D1 heartbeat at the expected cadence)
while the deployed bytecode was **stale**. The true chain of causes, in order:

1. **Node.js v16 vs Wrangler ≥ v22.** The Codespace ran Node v16.20.2; Wrangler 4.110
   refuses to run below v22 and **exited before upload**. Every "deploy" was a no-op.
   *This was the load-bearing root cause and it went undiagnosed for two days.*
2. **Stale working tree → Cloudflare error 10064.** A tree missing the `PumpTape`
   Durable-Object class deployed a bundle that live DOs depended on but that didn't
   export it. Fixed only by forcing the tree with `git reset --hard origin/<branch>`.
3. **`npx wrangler` install prompt canceled.** The interactive "Ok to proceed? (y)"
   cannot be answered through the mobile terminal; the install `npm ERR! canceled`.
4. **Symptom-for-artifact substitution.** The seat verified a downstream heartbeat
   instead of the deployed code, so a stale worker read as "fixed."
5. **`git log` stalled the Codespace.** `git log -1 --oneline` — used for the very
   verification MIB Rule 4 prescribes — glitched the mobile UI, a direct contributor
   to the lost terminals.

What the existing MIB covered: forge/contract verification via `report.txt` + `tee` +
`grep`. What it did not cover: a **deployed runtime artifact** (a Worker shipped via
`wrangler`), where deployed code and observed behavior can diverge. This amendment
closes that gap and reconciles the git-log rules with observed mobile reality.

## Correction 1 — Rule 4: never verify a commit with `git log`

**REMOVE** from §III Rule 4:

> Then verify with:
> ```
> git log --oneline -3
> ```
> Never trust "Everything up-to-date" — it can appear even when changes weren't
> actually committed. Always verify the commit landed via `git log` output.

**REPLACE WITH:**

> Never trust "Everything up-to-date" — it can appear even when changes weren't
> actually committed. Verify the commit landed **without `git log`** (see Rule 5),
> using any of:
> - the range printed by `git push` itself (e.g. `9b1a992..d4c0378`),
> - `git status --short` (clean tree = committed),
> - `git show --stat <ref>` for the specific commit,
> - `grep -n "<marker>" <file>` to confirm the intended change is in the tree,
> - the GitHub web UI commit view.

## Correction 2 — Rule 5: the `git log` ban is total

**REPLACE** the Rule 5 stall list entry for `git log` with:

> - **`git log` — BANNED IN EVERY FORM**, including `git log -1 --oneline`,
>   `git log --oneline -N`, and any flag combination. It stalls the mobile Codespace
>   UI and has cost live terminals. There is no "safe" invocation. Use the Rule 4
>   substitutes instead. (`git show --stat`, `git status`, `git diff --stat` are fine;
>   the banned token is `git log`.)

## Rule 7 — Verify the deployed artifact, never the symptom

**A downstream symptom — a heartbeat, a tick, a metric, a rendered page — can be
produced by OLD code. It is never proof that new code deployed.** Before claiming any
deploy-dependent state ("fixed," "live," "working," "deployed"), verify the **artifact**:
read the deployed code/version and confirm a marker **unique to the new code is present**,
and where possible that a marker **unique to the old code is gone**. Behavior checks —
heartbeats, feed cadence, rendered pages — are examined **only after** the artifact is
confirmed changed. A green symptom on unverified bytecode is a Prime-Directive violation.

### Verbal-tic corollary
"Confirmed," "verified," "the real fix," and their kin are reserved for statements
backed by a **shown check**. If the check was not run, the claim is not made.

### Trust the documented known-limitation
When a failure is already documented — in code comments, a prior `report.txt`, or a
council statement — that substrate is consulted and trusted **before** re-diagnosis.
Re-diagnosing a documented failure as novel is the anti-MIB.

## Addition to Rule 3 — Cloudflare Worker deploy-and-verify sequence

Rule 3 gives the canonical **forge** (contract) fresh-terminal sequence. Deploying a
**Cloudflare Worker** (the radar) is a different toolchain with its own exact sequence.
One command per numbered block (Rule 1); tee'd (Rule 6); no `git log` (Rule 5).

> **1.** `git fetch origin <branch>`
> **2.** `git checkout -f <branch>`
> **3.** `git reset --hard origin/<branch>`  — force the tree; kills stale bytes (10064).
> **4.** `grep -n "<new-code-marker>" <worker-dir>/<file>`  — Rule 4 tree-gate, not `git log`.
> **5.** `nvm use 22`  — or `nvm install 22` on a fresh Codespace. **Non-negotiable preflight.**
> **6.** `node -v`  — MUST read `v22.x`. Wrangler ≥4.110 refuses v16 and exits before upload.
> **7.** `cd <worker-dir>`
> **8.** `npm install`
> **9.** `export CLOUDFLARE_API_TOKEN=<token>`  — fresh each deploy; auto-disarms; never persisted.
> **10.** `npx --yes wrangler deploy 2>&1 | tee ../deploy_report.txt`  — `--yes` skips the
>          install prompt that cancels on mobile.
> **11.** `grep -iE "Version ID|Total Upload|error|10064|<DO-class>" ../deploy_report.txt`
> **12. THE LOAD-BEARING STEP —** read the **live deployed** worker
>          (`workers_get_worker_code`) and grep a marker unique to the new code
>          (and confirm an old-code marker is gone). Only now is the deploy proven.

The Node-22 preflight (steps 5–6) is the single check that would have prevented the
entire saga. It is not optional. Step 12 is the Rule 7 gate and precedes any behavioral
(D1/feed) check.

## Verification (this amendment's own substrate)

- Node cause: three Codespace screenshots showed
  `Wrangler requires at least Node.js v22.0.0. You are using v16.20.2.`
- 10064 cause: `deploy_report_3` showed error 10064 on a 663 KiB stale tree; the fixed
  tree deploys at ~720 KiB with `env.PUMPTAPE (PumpTape) Durable Object` bound.
- npx cause: `deploy_report_4` showed `Ok to proceed? (y) npm ERR! canceled`.
- Successful deploy (`deploy_report_5`): 720.09 KiB, Version ID
  `cb1b43b0-6cae-4725-b98b-a1da9dafc269`, no error.
- Artifact proof (Rule 7): live bytecode grep showed `var PumpTape = class` present and
  exported, `screenScan` called from cron, old `SUB_TICKS`/`RadarScanner` absent.
