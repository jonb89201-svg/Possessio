## Findings — contracts (src/)

### V-1 · MEDIUM — a honeypot/zero-liquidity position permanently ratchets the FundingVault's outstanding cap
`src/PossessioRail.sol:176,197` + the vault's `returnProceeds` path. A drawn position's
`outstanding` is only ever cleared by `FundingVault.returnProceeds` (`onlyTrader` = the
Rail), which the Rail calls only after a *successful* token→USDC swap. Both Rail exits
require `minUsdcOut > 0` (`exit` :176, `ownerExit` :197) and there is no zero-proceeds /
abandon path anywhere. A token that can't be sold for ≥1 unit USDC — a honeypot that
blocks sells, or a zero-liquidity rug — makes the position permanently un-closeable, so
its draw stays in `vault.outstanding` forever. Since the product trades human-picked Base
meme coins, honeypots are in-scope. Impact is **availability, not fund loss** (the capital
is already gone in the rug): each dead position ratchets `outstanding` up, and the operator
must keep raising `maxOutstanding` (24h-timelocked each time) to keep trading. `withdraw`
is unaffected (it binds on `available() == balanceOf`, never on `outstanding`).
**Fix direction:** an owner-only `abandonPosition(intentId)` on the Rail that marks the
vault trade closed via `returnProceeds(intentId, 0)`.

### R-1 · LOW — Rail `sweep` doesn't protect a currently-open position token
`src/PossessioRail.sol:205-212`. `sweep` blocks only `usdc` (:208) and transfers the entire
balance of any other token to the owner. If a position is Open in that token, `sweep`
removes the tokens backing it; the subsequent `exit`/`ownerExit` swap then reverts (nothing
to sell) and the position + `outstanding` become stuck (compounds V-1). Owner-only, so not
an external attack — but an unguarded foot-gun. Skip/revert on tokens with an Open position,
or document the interaction.

### SIZE · LOW/INFO — the hook has a 409-byte EIP-170 margin; `optimizer_runs=200` is load-bearing
`foundry.toml` (uniform `optimizer_runs = 200`, commit 82872d5) + `PossessioHook`.
The build confirms the hook runtime is **24,167 bytes — only 409 under the 24,576 limit**.
`runs=200` is therefore load-bearing for deployability (a higher setting pushes the hook
over EIP-170), and the header's account of why per-contract restrictions couldn't include
the hook is accurate. Not a bug today, but any non-trivial future addition to the hook risks
making it undeployable. Track the margin.

### S-1 · INFO — no pinned deploy scripts for the three new organs
`script/`. `PossessioFundingVault`, `PossessioRail`, and `PossessioAutoTarget` are stood up
only via the predict-then-prewire CREATE pattern inside their test suites; there's no
scripted, address-pinned runbook for the production vault↔Rail prewire (the vault's immutable
`trader`/`tradeDestination` must equal the predicted Rail address). A prewire mistake bricks
the pair permanently — the same CREATE3-freeze class the constellation scripts already guard
against. Add pinned deploy scripts before mainnet.

### INFO — cbETH principal is permanently non-withdrawable from the hook (by design)
`src/POSSESSIO_v2-6-3.sol:2170`. C-1's fix harvests only exchange-rate *appreciation*;
`rescueToken` still blocks cbETH, so principal never leaves. This is the intended
perpetual-endowment posture (the C-1 fix direction offered value-based harvest *or* a
treasury-gated withdrawal; only the former was built). The critical trap — a dead harvest
branch — is resolved. Worth stating explicitly for operators so the principal lock isn't
mistaken for a bug.

**Prior contract findings — all verified resolved:** C-1 (value-based cbETH harvest via
`cbETHPrincipalETH` + `_readCbEthRate`; `checkUpkeep` HARVEST branch can now fire), C-2
(`sendUSDC`/`sendCbETH`/`redeemMorpho` now consume daily limits; redeem + sendUSDC share the

## Findings — workers (radar / console / public console)

### N-1 · HIGH — council ledger POST: unauthenticated, replayable writes into the production radar D1
`worker/index.ts:194-240` + `radar/migrations/0024_council_ledger.sql:10-19`. Four gaps compound:
- **Nonce is signed and stored but never checked.** The insert (:233-237) has no uniqueness
  guard and 0024 has no `UNIQUE(seat, nonce)`, so the same `(body, nonce, signature)` triple
  inserts successfully forever.
- **GET is public and returns `signature` + `nonce`** (:200-204). Any anonymous party can
  harvest a legitimate seat's signed statement and re-POST it in a loop; every replay passes
  `recoverTypedDataAddress`, passes the allowlist (the seat *is* a seat), and lands as a fresh
  row with a new server `ts_ms`.
- **`COUNCIL_SEATS` is not set in `wrangler.jsonc`.** With `allow.length === 0` the seat check
  at :230 is skipped entirely — **any address that signs its own statement can append**, no
  council membership required.
- **No rate limit, and `kind`/`ref` are uncapped** (:211-212); only `body` is bounded (8000
  chars).

Blast radius is proven, not theoretical: the ledger lives in the radar's D1
(`possessio-radar-ledger`), and `radar/watcher.ts` documents the 2026-07-16 incident where
hitting the D1 size ceiling **halted every radar write**. An attacker looping 8KB POSTs (or
one oversized `ref`) refills the DB toward that cap and takes the radar down, while also
flooding the council channel with replayed statements the console renders as new.
**Fix:** `UNIQUE(seat, nonce)` + `INSERT OR IGNORE` → 409; cap `kind`/`ref`; require
`COUNCIL_SEATS` non-empty before accepting POSTs; per-IP/seat KV rate limit (same pattern as
the drip endpoint). *The EIP-712 crypto itself is sound — domain deliberately omits
chainId/verifyingContract so a statement can't replay as an on-chain vote; the defect is the
missing replay/rate/allowlist enforcement around it.*

### N-3 · MEDIUM — the R-1 fix's slimmed birth-JSON drops `associated_bonding_curve`, corrupting the just-calibrated rug gate
`radar/watcher.ts:71-80`. For payloads >4000 chars, `rawBirthJson` keeps only a 7-field
subset that omits `associated_bonding_curve`. But `radar/screen.ts:493-496` (migration 0020,
added *after* the R-1 fix) reads exactly that field to exclude the bonding-curve token account
from the float in `topHolderShare`. With `curveAcct = null`, the curve — the largest token
account by far pre-graduation — is counted as the top non-curve holder
(`screen.ts:184-194`), so the share lands near 1 → `gate_rug = 0` (a false "whale" rug fail,
`screen.ts:496`), which suppresses `strat_take` (:517). Any coin whose birth payload exceeds
4KB (a long creator description is enough) is silently mislabeled a hard rug fail in the very
ledger the calibration exists to keep honest — the same ledger-poisoning failure mode
migration 0023 was ratified to prevent, in the opposite direction.
**Fix:** add `associated_bonding_curve` to the slimmed subset.

### N-2 · MEDIUM — `/api/radar/candidates` proxy fetch has no timeout (repo bounded-fetch law, on a request path)
`worker/index.ts:52-54`. The console-worker proxy fetches the radar worker with no
`AbortSignal.timeout` — the exact violation class the repo's own law bans (documented at
`radar/watcher.ts:48-51` and the R-5 fix comment). A hung radar worker leaves every desk poll
(every 5s per open desk) hanging on the console worker until the platform kills it. The health
endpoint right below it does it correctly (AbortController + 3s). One-line fix.

### N-4 · LOW — `/api/radar/health` is an unauthenticated, uncached amplification path to a third-party RPC
`worker/index.ts:77-186`. Every request runs a 6-subquery D1 read, and whenever
`births_5min === 0` also POSTs to the public Solana mainnet RPC (:124-129). The fetch is
correctly bounded (3s) and fail-soft, but there's no caching or rate limit — during any real
lull, many open MIB panels (or an attacker) make the worker hammer the public RPC at request
rate, getting its egress IP rate-limited and degrading the very diagnosis the endpoint exists
for. Cache the verdict for 10-30s.

### N-5 · LOW — `radar/schema.sql` drifting again
Omits `council_ledger` (migration 0024, applied to the same DB the file claims to mirror);
header still says "as of migration 0018" while including 0019-0022. Same failure mode as the
prior audit's R-3, caught earlier this time.

### INFO — coin image URLs escaped but scheme-unvalidated (N-6); two innerHTML sinks fed unescaped radar numbers (N-7)
`radar/feed.ts:203-204` / `public/index.html:3382` load any `http(s)`/`data:` `image_uri`
(creator-controlled) — no XSS (attribute-escaped, and `javascript:` in `img src` is inert),
but a per-viewer tracking pixel; apply the R-10 `https:`-whitelist for symmetry.
`public/index.html:3410` and `radar/feed.ts:417-418` interpolate a radar `COUNT(*)` into
`innerHTML` unescaped — not exploitable without compromising the radar worker itself, noted
for completeness.

**Prior worker findings — all verified fixed:** R-1 (valid slimmed JSON + `json_valid()`
guard — but see N-3 for the side effect), R-3/R-4/R-5/R-6/R-8/R-9/R-10, W-3 (farcaster
`accountAssociation` now filled), W-4 (TestnetFuel `escapeHtml`). The new AI trading desk,
council-ledger console view, Transactions view, FundingVault operator panel, and cockpit
WebSocket were reviewed for XSS/auth/injection and are clean (every dynamic string routes
through `esc()`/`textContent`; the buy path signs on the user's own vault with client checks
that the contract re-enforces; explorer URLs from a hard-coded chain-ID whitelist).

## Findings — MCP servers / mailer

### XT-1 · MEDIUM — xtrade caps are checked against caller-claimed `notionalUsd`, but the trade is built for caller-supplied `amountAtomic`
`mcp/xtrade/server.js:82-84,133,137-139`. The daily/per-trade caps check `a.notionalUsd`,
while the swap is quoted and built from `f.amountAtomic` — the two are never reconciled. Call
`build_trade` with `notionalUsd: 1` and a huge `amountAtomic`: caps pass ($1 ≤ $2), an unsigned
swap for ~$160k is built and returned, and the ledger records `notionalUsd: 1`. Both the
$2/trade and $20/day exposure caps become accounting fiction relative to the real payload, and
Sec5 exposure truth is corrupted for builds. Bounded today because the output is unsigned and
the Architect signs on device — but this is the W-2-class latent bypass the moment hot mode is
wired. **Fix:** derive USD notional server-side from `inputMint` + `amountAtomic` (the SOL/USDC
price is already fetched in `facts.js`) and cap on that, refusing on large divergence from the
claimed notional.

### CS-1 · LOW — council-signer `/healthz` is unauthenticated and discloses the seat address
`mcp/council-signer/remote.js:79` returns `{ok, seat, chainId}` before the bearer check (:84),
and `deploy.sh:58-60` instructs making the Codespace port PUBLIC. Anyone who scans the URL
learns "this host holds council seat 0x… on chain 8453" — free targeting intel, no token
required. Return `{ok:true}` only, or gate the seat/chain detail behind the bearer.

### XT-2 · LOW — xtrade rug gate trusts the radar tape for creator *identity* while labeling the fact chain-read
`mcp/xtrade/facts.js:474-487`. `creatorHoldingPct` reads the creator's balance on-chain (truth)
but takes the creator *address* from the radar tape (class 3), then tags the whole fact
`solana-rpc` (class 1), satisfying `hotFactsGuard`. A compromised radar/D1 can plant a decoy
creator holding ~0% on a rugged token → the check passes while being classed a chain read.
Verify the creator from chain (first-mint signer — the signature walk already runs), or
downgrade the fact's source class when the address came from the tape.

### XT-3 · LOW (latent) — xtrade `execute_trade` has no caps/rug/entry/session gates of its own
`mcp/xtrade/server.js:162-203`. All Sec0-3 gating lives only in `build_trade`; the hot path
just runs `resolveMode` → `hotFactsGuard` → hard-refuse ("hot signer not wired"). Safe today,
but nothing structurally forces the full gate/caps pipeline to be re-applied when a signer is
eventually wired at :200. Flagging so the future hot wiring doesn't ship ungated.

### XT-5 · LOW — xtrade has no committed lockfile
`mcp/xtrade/` bears dependencies (`@modelcontextprotocol/sdk`, `zod`) but ships no
`package-lock.json`, despite the repo's own `.gitignore:20-21` doctrine that lockfiles are
committed. `npm install` at deploy freshly resolves the ranges — the same unpinned-supply-chain
class as the prior R-2, into the trading server. Mitigating: xtrade is a local server, not
CI-deployed. Commit a lockfile.

### INFO — council-signer hardening notes (CS-2/CS-3/CS-4)
No rate limit on bearer 401s (irrelevant with a ≥32-char random token); `council_approve_by_sig`
`expiry` is unbounded caller input (a server-side ceiling, e.g. now+7d, would cap a leaked
signature's lifetime); the statement domain is chain/contract-agnostic by design (replayable to
a future ledger — the 256-bit random nonce makes it dedup-able, so acceptable as
attribution-only). `mcp/xtrade/server.js:225` binds a stdio transport at import (no
`require.main` guard) — cosmetic.

**Prior MCP/mailer findings — all verified fixed, no regressions:** W-1 (builds recorded
`outcome:"built"`, never `"filled"`; caps still count builds, performance truth reads only
fills), W-2 (gates run on server-fetched facts via `gatherFacts`; caller facts compared for
divergence only; fail-closed on `UNAVAILABLE`), W-5 (mailer `/status` bearer-gated,
constant-time, fail-closed, 404 no-oracle; send path cron-only), W-6 (solana-mcp
`ACCESS_KEY.length < 32`). The new council-signer remote signer was deep-reviewed as production
key infrastructure: the seat key is loaded from env into a non-enumerable frozen property,

sound (statement ≠ vote ≠ tx; preimage is hook-address-bound); `deploy.sh` never echoes secrets;
the committed lockfile has zero git deps and zero install scripts. solana-mcp (read-only
allowlist, capability-URL auth, dependency-free) and mailer (fully parameterized D1, secrets
never logged) are clean; the mailer cold-outreach unsubscribe-link gap remains a business call.
