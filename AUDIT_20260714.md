## Findings — contracts (src/)

### C-1 · HIGH — v2.6.3 hook: cbETH treasury is permanently trapped; harvest can never fire
`src/POSSESSIO_v2-6-3.sol:1360-1362` (`_harvestRewards`) computes rewards as
`cbETH.balanceOf(this) - cbETHPrincipal` and reverts if not positive. But cbETH is
non-rebasing — `balanceOf` never grows (the contract's own comment at :1182-1184 says
rewards accrue via exchange-rate appreciation) and `cbETHPrincipal += cbReceived` (:1267)
tracks the balance exactly. So `cbBal == cbETHPrincipal` always → harvest always reverts
`ZeroAmount`, and the `checkUpkeep` HARVEST branch is dead. There is **no other cbETH
exit**: `rescueToken` blocks cbETH (:1965), `savSlash` moves only STEEL. 75% of every
captured fee converts to cbETH that can never leave the hook.
**Fix direction:** value-based harvest (principal in ETH-wei at deposit-time rate, harvest
the rate-appreciation excess via the existing oracle) and/or a treasury-gated cbETH
withdrawal path.

### C-2 · MEDIUM — Payments: compromised-key protection only covers the DAI leg
`src/PossessioPayments.sol` — `sendUSDC` (:1292), `sendCbETH` (:1310), `redeemMorpho`
(:1330) let OWNER move full balances in one call. The daily limit applies only to
`withdrawDAI`; the 7-day timelock only to the emergency path; the Guardian freeze is
optional and defaults off (:418). A stolen merchant key drains USDC/cbETH/Morpho instantly.
Either extend the limit/timelock to those paths or drop the compromised-key claims in docs.

### C-3 · MEDIUM — PLATE.sol (superseded v1) still in src/ with the known Base-bricking bug
`src/PLATE.sol:780,786` calls `cbETH.deposit{value:}` / `rETH.deposit{value:}` directly —
the exact defect v2.5 was rebuilt to fix (reverts on Base; OptimismMintableERC20 has no
payable deposit). If PLATE is history, move it out of `src/` (it also compiles into every
build); if it's live anywhere, its `routeETH` halts once `toStaking > 0`.

### C-4 · LOW — Hook: permissionless `routeETH` caller reward is a no-op in practice
`src/POSSESSIO_v2-6-3.sol:1040-1049` pays the 0.1% reward only if
`address(this).balance >= reward` **after** routing spent the entire accumulator. Unless
the hook holds untracked surplus ETH, the guard fails and the reward silently skips.
(Unit test passes because the harness deals surplus ETH.) The v2.6.2→v2.6.3 changelog
about fixing this path is therefore only half-true.

### C-5 · LOW — `FeeCaptured` logs `tx.origin` as the swapper (`:929`); indexers will
misattribute router-mediated swaps. Event-only.

### C-6 · LOW — `PLATEStaking.emergencyWithdraw` (:110-119) zeroes `totalStaked` but not
per-member `staked[]` (acknowledged in-code); a later re-stake double-counts in `getStaked`.

### C-7 · INFO — `DeployPayments.s.sol:34` supplies a DAI/USD feed where the contract doc
(:403) says DAI/ETH. Only freshness is read, so no fund impact — but align doc and deploy.

Clean on review: PossessioPool, PossessioX402Core (nonce-commitment binding sound),
PossessioFactory, PossessioSaltPool, L1Anchor/Factory, SAV, TestnetLaunchPool,
LSTExchangeRate, SymmetryGuardCore/HandshakeLib.

## Findings — radar worker

### R-1 · HIGH — truncated `raw_birth_json` can 500 the public feed (externally triggerable)
`radar/watcher.ts:98` stores `JSON.stringify(it).slice(0, 4000)` — payloads over 4000 chars
become invalid JSON. `radar/x402-toll.ts:208-209` runs `json_extract(b.raw_birth_json,…)`
over it on every `/radar/candidates` poll, and SQLite **throws "malformed JSON"** on a
truncated document (verified against node:sqlite). A creator-controlled >4KB birth payload
(e.g. long description) that qualifies as early/candidate 500s the feed for as long as the
row is in the top-40 window; the page silently shows stale data (`poll()` swallows it,
`feed.ts:475`). Fix: don't truncate mid-JSON (extract the few needed fields, or validate
before store, or `try/catch`-equivalent via `CASE WHEN json_valid(...)`).

### R-2 · MEDIUM — no lockfile → unreviewed supply-chain into the production toll worker
`.gitignore` globally ignores `package-lock.json`; CI's `npm ci || npm install` always falls
through to fresh resolution of `@x402/*` / `hono` ranges + latest wrangler on every
scheduled deploy. A bad upstream release ships to production automatically. Commit
lockfiles (remove the ignore) and drop the `|| npm install` fallback.

### R-3 · MEDIUM — `schema.sql` badly drifted from migrations
Header claims "repo mirror" but reflects only base + 0003-0005. Missing: `spends`,
`regime_ticks`, `candidates`, `earlies`, `mc_ticks`, `early_cycles`. A fresh DB provisioned
from it fails on most writes in screen/pumptape and reads in x402-toll.

### R-4 · MEDIUM — migration 0017 is a guaranteed no-op; its diagnosis is false
`0009_earlies_ticks.sql:30` already created `idx_mc_ticks_ms`; `0017` re-issues the identical
`CREATE INDEX IF NOT EXISTS`. The "340MB full-scan prune contributed to the stall" analysis
recorded for 0017 therefore changed nothing — part of the tape-stall root cause remains
unvalidated.

### R-5 · MEDIUM — `getNews()` breaks the repo's own bounded-fetch law on the request path
`x402-toll.ts:93-97`: three sequential RSS fetches with no `AbortSignal.timeout`, awaited
inside `GET /radar/news`, with a cache-stampede on expiry. watcher.ts:39 documents exactly
why this is banned ("hung upstream froze the scan 21min").

### R-6 · MEDIUM — `PumpTape.ensure()` un-timed WS-upgrade fetch can kill the alarm chain
`pumptape.ts:142-144` has no timeout, and `alarm()` re-arms only **after** awaiting
`ensure()` — a hung upgrade consumes the fired alarm and never sets the next one; every
per-minute cron poke then enters the same hang. Arm the next alarm before fallible work.

### R-7 · LOW — the single-pass rework still runs all five jobs in one 30s CPU budget
(`index.ts:18-35`) — the failure mode diagnosed in 758fd5d returns as data grows, and the
DO-era staleness monitor was removed with the DO. Acceptable stopgap; needs a watchdog.

### R-8 · LOW — `/radar/session-gate` charges $0.01 (when toll armed) for a permanent
`NO_READING_YET` error — nothing ever writes `sessions` (or `trades`/`spends`).

### R-9 · LOW — `feed.ts` defines `pf`/`spark`/`roc` **twice** (lines ~201-218 vs ~267-281);
hoisting makes the second set silently win; the dead first set differs (slice(-16) vs -14,
different flat-rendering) and will mislead future edits.

### R-10 · LOW — news link hrefs are escaped but not scheme-validated (`feed.ts:466`);
a compromised RSS feed could emit a clickable `javascript:` URL. Whitelist `http(s):`.

### R-11 · INFO — dead `screenLoop` export (`screen.ts:151`) and `SPEC_BACKEND.md` still
document the removed 15s sub-tick/DO architecture; `index.ts` header still says the
watcher is "not yet landed" while importing it.

## Findings — console worker / mailer / MCP servers

### W-1 · MEDIUM — xtrade ledger records unsigned builds as `outcome:"filled"`
`mcp/xtrade/server.js:105` — every `build_trade` (an *unsigned* payload) writes a "filled"
row with full notional. Ten unsigned builds exhaust the $20 daily cap and pollute the
Sec5 ledger whose purpose is verifiable net-return truth. Record `outcome:"built"` and
count caps on confirmed fills (or keep counting builds for caps, but never label them filled).

### W-2 · MEDIUM — xtrade safety gates run on caller-supplied "facts"
`server.js:76` — `mintRenounced`, `lpLockedOrBurned`, `creatorHoldingPct`, `mc`, etc. come
straight from tool args; no on-chain verification exists in the shipped server despite
selection.js's "come from chain reads" comment. Harmless today (hot mode unwired, nothing
executes) but it is the latent bypass the moment a signer is wired per Sec4.

### W-3 · MEDIUM — `public/.well-known/farcaster.json` `accountAssociation` is blank
(header/payload/signature all `""`) — the mini-app can't verify domain ownership until the
signed JFS triple is filled (the enrichment commit 1669f38 didn't cover it).

### W-4 · LOW — TestnetFuel renders error strings via `innerHTML` unescaped
(`public/index.html:2903` → sink at :2928), unlike the rest of the console which routes
through `escapeHtml`. Crafted RPC/revert text renders as markup.

### W-5 · LOW — mailer `GET /status` is unauthenticated (lead-pipeline counts leak);
send path itself is cron-only (no open relay), D1 fully parameterized. Also note: cold
outreach with no unsubscribe link is a CAN-SPAM/GDPR exposure (business call, not code).

### W-6 · INFO — solana-mcp enforces `ACCESS_KEY.length >= 16` where its own doc says ≥32
